## Was du in Session 020 erledigen sollst

**Ziel:** Voice-Ingest end-to-end verifiziert und produktiv in Nutzung — eine echte Sprachnachricht an den Bot erzeugt einen korrekten Wiki-Fact.

### Was am Ende existieren soll

1. Eine echte per Telegram-Voice geschickte Nachricht ist als PersonalFact und/oder VocabEntry im Wiki gelandet.
2. `language_detected` im raw_event stimmt mit dem tatsächlich Gesprochenen überein (DE / ES / Mix).
3. Mindestens ein Testfall für **jede** dieser Situationen ist gelaufen:
   - Kurze deutsche Sprachnachricht (< 15s)
   - Kurze spanische Sprachnachricht (< 15s)
   - Längere Sprachnachricht mit DE/ES-Mischung (30–60s)
   - Sprachnachricht mit moderatem Hintergrundgeräusch
4. Falls Bugs/Edge-Cases auftreten: repariert **oder** klar in `hinweise/technischer_hinweis.md` dokumentiert (inkl. Reproduktionsschritte).
5. I6-Fehler-InlineKeyboard ist nebenher durch einen echten Fehlerfall verifiziert (aus S018 offen geblieben — kein Blocker, aber wenn Voice schiefgeht, nutze die Gelegenheit).

### Was wichtig ist (und was nicht)

**Wichtig:**
- Korrekte Sprach-Detection (Whisper `info.language`) — das entscheidet über Routing in Language-Agent vs. Diary-Agent.
- Performance bei echter Länge: Whisper "small" auf CPU/int8 dauert wie lange für 30s Audio? Wenn > 15s Wartezeit → Usability-Risiko; dann ist "⏳ Verarbeite..." zu nackt.
- Fehler beim ersten Modell-Download (lazy-load in `_get_model()`): erster Call zieht das "small"-Modell. Das ist ein stilles Friction-Risiko bei Erstnutzung — dokumentieren oder vorab-warmen.

**Nicht wichtig (nicht hineinziehen):**
- Story-Lab-Voice-Coaching / Tonalitätsanalyse — das bleibt gestrichen (ENT-024).
- Anki-Export — MVP-2-Zweitwelle, separate Session.
- Voice-Modus-Schalter / Sprach-Override per Command — UX-Frage für später.

## Technischer Umblick — wie der Voice-Pfad heute aussieht

Wichtig für dich zu wissen: **der Code ist da.** Das ist kein Neu-Bau.

### Was existiert

| Komponente | Stand |
|---|---|
| `agents/extractors/audio_extractor.py` | Voll implementiert: faster-whisper "small", int8, CPU, Sprach-Detection via `info.language`. Schreibt permanente Kopie nach `raw/assets/` wenn Input außerhalb wiki_root liegt. |
| `faster-whisper>=1.0.0` | In `requirements.txt` |
| `Extractor._extract_audio()` | Dispatch bei `.ogg/.opus/.mp3/.m4a/.wav/.flac` (extractor.py:145) |
| `bot.handle_voice` | Speichert `.ogg` nach `raw/assets/`, ruft `_extractor.extract(dest)` (bot.py:258-262) |
| `handle_video` | Nutzt `_extract_video_audio` → `ffmpeg` → Audio → Whisper. Ebenfalls da, ungetestet. |

### Was fehlt / was unsicher ist

1. **Noch nie im echten Voice-Flow gelaufen.** Session 018 schrieb "Voice/Foto-Handler vorhanden aber ungetestet" — das gilt weiterhin.
2. **Modell-Download beim ersten Call** blockt synchron im `asyncio.to_thread(run_ingest, ...)`-Kontext → erster Nutzer-Voice → langer Stille-Block. Warm-up oder `⏳ Lade Transkriptionsmodell (einmalig)...` wäre freundlich.
3. **`language_detected`** wird im `ExtractedContent` gesetzt, aber ich weiß nicht, ob der Supervisor-Classify und der Language-Agent das konsistent aufgreifen — bitte ende-zu-ende prüfen.
4. **ffmpeg-Dependency** für Video — nicht in requirements, System-Dependency. Falls Test auch Video abdecken soll: dokumentieren oder Video-Handler aus MVP-2-Scope rausnehmen.
5. **Python 3.14 + faster-whisper-Wheel** — bei erstmaligem `pip install` kann es zu Kompilierungsfehler kommen. Fallback auf Python 3.12 ist bereits als ENT-033-Risiko bekannt. Wenn bei dir `pip install` sauber durchgeht: vermerken, dass Wheels verfügbar sind.
