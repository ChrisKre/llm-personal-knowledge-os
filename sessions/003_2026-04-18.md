## Systemkontext

**Was ist dieses System?**
LLM-Personal-Knowledge-OS: ein persistentes, kompiliertes persönliches Wissens- und Persönlichkeitssystem. Basiert auf Karpathys LLM-Wiki-Konzept. Kein RAG — kompiliertes, vernetztes Wissen in Markdown-Dateien, gepflegt von LLM-Agenten, navigierbar über Obsidian.

**Tech Stack (final entschieden):**
- Python + Claude API: Haiku 4.5 (Bulk/Klassifikation), Sonnet 4.6 (Synthesis/Coaching), Ollama (sensitivity:private)
- LangGraph — explizite Zustandsmaschinen, debuggbar
- Markdown + Git — Wissensspeicher, Obsidian-kompatibel, versioniert
- Telegram Bot — primärer Input-Kanal (Text/URL/Bild/PDF/Voice/YouTube)
- AnkiConnect REST — Vokabel-Export (für COMP_LANGUAGE.md)

## Architektonische Bedenken (vom Architect aus Session 003)

**1. requirements.txt fehlt — nächste Priorität:**
Kein `requirements.txt` vorhanden. Alle Imports in den Scaffold-Dateien setzen folgende Packages voraus:
- `anthropic` (Claude API)
- `langgraph`
- `requests`, `beautifulsoup4` (URL-Extraktion)
- `pdfplumber` (PDF)
- `faster-whisper` (Audio)
- `youtube-transcript-api` (YouTube)
- `python-telegram-bot` (Telegram)
- `watchdog` (File-Watcher für raw/sources/)
Eine `requirements.txt` mit diesen Abhängigkeiten sollte als erstes in Session 004 erstellt werden.

**2. Supervisor-Nodes fehlen als echte LangGraph-Integration:**
`supervisor.py` hat `classify()`, `route()`, `review()` als Methoden — aber der übergeordnete LangGraph-Workflow der alle Nodes verbindet (aus ARCHITECTURE.md §5.1) existiert noch nicht als Python-Datei. Es fehlt eine `main_workflow.py` die den Hauptgraphen aufbaut.

**3. Diary-Agent und Language-Agent Nodes alle `raise NotImplementedError`:**
Die Stubs haben die richtige LangGraph-Struktur, aber keine einzige Node ist implementiert. Empfohlene Reihenfolge für Session 004:
- `diary_agent.extract_fact()` + `score_main()` — zusammen den Haupt-Ingest-Pfad lauffähig machen
- `language_agent.detect_words()` + `create_vocab()` — analog für Vokabeln

**4. Telegram-Bot-Grundgerüst fehlt komplett:**
Kein `bot.py`, kein Webhook-Setup, keine `python-telegram-bot`-Integration. Das ist der primäre Input-Kanal — ohne ihn kann das System nicht mit echten Inputs getestet werden.

**5. graph_reader._extract_keywords() nutzt kein LLM:**
Aktuell regelbasiert (Regex + Stopword-Filter). Das ist OK für Phase 1, aber bei komplexeren Inputs (langer Fließtext, Voice-Transkript) wird die Qualität schlecht sein. Spätestens ab 20+ PersonalFacts sollte auf Haiku-basierte Keyword-Extraktion umgestellt werden.

## Kernkonzepte (Wiederholung für neues Claude-Fenster)

**Graph Context Match:** Vor jeder Agenten-Ausführung werden Top-N relevante Wiki-Seiten für den aktuellen Input geladen (`graph_context`). Agenten bewerten nie isoliert.

**Zwei State-Ebenen:**
- `user_profile.md` (~80-120 Zeilen) — komprimierte Nutzer-Signatur, immer im Kontext
- `graph_context` — dynamisch per Task, konkret relevante Wiki-Seiten

**Draft→Main Workflow:** LLM schreibt immer auf `draft`-Branch. Kritische Änderungen brauchen Nutzer-Freigabe via Telegram-Button → Python `git merge`.

**Extractor-Layer:** Normalisiert alle Input-Formate in dasselbe JSON-Schema. Pipeline sieht immer nur Text. Zwei Modi: Quick-Save vs. Process-Now.

**Sensitivity-Tier:** public→Haiku, sensitive→Sonnet+PII-Strip, private→Ollama (verlässt nie das Gerät).

**WikiWrite-Vertrag:** Kein Agent schreibt direkt Dateien. Alle schreiben WikiWrite-Objekte in den State. graph_writer führt nach Supervisor-Freigabe aus.
